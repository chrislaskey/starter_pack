# Dynamic forms in every app

A form is defined once as SurveyJS compatible subset JSON and works the same in
the web app and the desktop app: the same fields, the same markup, the same
rules and the same error messages. The web app renders it with the
[`dynamic_form`](https://hex.pm/packages/dynamic_form) library; the desktop app
renders it with the Svelte mirrors of the same components and validates it in
Rust by the library's rules. The post form on `/posts` and on the desktop
communities page is the first one.

This document records what was built, the decisions behind it with the
alternatives considered, what is not supported yet, and what the
`dynamic_form` library could change to make this easier.

### A change, end to end

Web: the library's LiveComponent gets `phx-change`, builds a changeset
with `DynamicForm.Changeset.create_changeset/3`, and re-renders through
`CoreComponents.input/1`. On a valid submit it sends
`{:dynamic_form, :success, payload}` to `PostsLive`, which calls
`Posting.write/3`; that still runs `Post.changeset/3`, the universal
changeset, as the authority. After a post the LiveView bumps the
component's id, which mounts a fresh, empty form.

Desktop: `show_post_form` mounts the form, as the LiveComponent does
when it first renders: the crate's `DynamicForm::mount`. On every `input`
event `DynamicForm.svelte` sends the form's `FormData` entries with the
`state` the last view came with, and `change_post_form` decodes the
entries the way Plug does (`ecto_changeset::form::decode`), merges them
over the state as the component merges over its changeset, validates,
and returns the view and the new state. Only the reply to the latest
request is applied. `write_post` submits the same way and writes the
post when the form is valid (where `store::write_post` runs
the universal changeset again, as the server does), or returns the form
with every error showing. A written post remounts the form with `{#key}`.

## Decisions

### Data mode only

Only the JSON definition is supported, not `<:field>` slots. A definition
in data is the only kind both apps can read. Slot bodies (custom
controls, content blocks) are HEEx closures and cannot cross over.

### One components module, `CoreComponents`, on universal field components

`dynamic_form` calls a components module's `input/1` with a
`Phoenix.HTML.FormField`, and Phoenix's `input/1` turns it into an id,
name, value and errors before its template, across several clauses.
`mix app.svelte` can't mirror that: it needs one clause whose whole body
is a template. So the work is split in two, inside `CoreComponents`:

* `input/1` keeps Phoenix's API and does the `FormField` to props step:
  id, name (with `[]` for lists), value, translated errors once the input
  is used, and options normalized to `%{label, value, selected | checked}`
  maps. Each type clause then renders a form field component. It has no
  markup of its own, except for hidden inputs.
* One single-template component per field kind, `text_input/1` and so on,
  marked `@universal_component true`, renders from those props only. These
  mirror into Svelte unchanged.

`App.Web.CoreComponents` is then the module passed as `components=`, so
the library's questions and the app's hand-written forms render the same
way, and both mirror into Svelte. What the library needs beyond Phoenix's
`input/1` came from its own `DynamicForm.CoreComponents`:

* `required` as an attr, rendered on the control and as the mark beside
  the label, and `required_label` (`"*"`, or `nil`/`false` for none).
  Since `required` is no longer just an HTML attribute, the auth and
  settings pages' required fields now show the mark too.
* `type="radio-group"` and `type="checkbox-group"`, with `options` and a
  `layout`. The library calls `input_radio_group/1` and
  `input_checkbox_group/1` by name, with `style: :vertical`; those two
  functions turn `style` into `layout` and call `input/1`.
* `range` among the types.
* `button/1` declares `type` and `disabled`, because the library passes
  them beside an explicit `rest`, and Phoenix only gathers undeclared
  assigns into `rest` when none is given.

Each field component takes `{@rest}` for the rest, so `autocomplete`,
`placeholder`, `readonly`, `rows` or `phx-debounce` reach the control, and
the Svelte mirror spreads `...rest` the same way. The ones declared as
attrs are what the markup itself needs: `disabled` on the checkbox
components, whose hidden input needs it too, and `class` and
`error_class`, Phoenix's overrides.

The Rust `view` does the same props step for the desktop app, so the
generated Svelte gets the same props the HEEx gets.

The props are chosen to be JSON-friendly: choices as maps rather than
tuples (`options_for_select/2` is a function call the generator rejects,
and with it option groups aren't supported), and the group layout as
`"vertical"`/`"horizontal"` instead of atoms.

Alternatives considered:

* **A separate adapter module, `App.Web.FormComponents`, passed as
  `components=`.** That was the first version: an adapter with the
  library's function names and no markup, next to Phoenix's untouched
  `input/1`. It made two input systems where one does, and the
  hand-written forms couldn't be mirrored. Its only real job, the
  `FormField` to props step, is what `input/1`'s first clause already
  did.
* **Put the field components in their own module.** The
  `core_component_tags` app check only allows raw `<input>` and `<button>`
  tags in the components modules it lists, and adding a module means
  editing `.app_checks.exs`, a protected lint config. The check's intent
  is the same as this design's: the markup lives in one module.
* **Hand-write `Input.svelte` as a mirror of the multi-clause `input/1`**,
  like `Button.svelte`. That works but drifts by hand; generated files are
  checked by `mix test`.

`CoreComponents.error/1` stays private: the field components are in the
same module. The library's `label/1`, used around slot bodies, isn't
provided, so the library's own is used; data mode has no slot bodies.

### A separate Rust crate on top of `ecto_changeset`

`native/dynamic_form` is its own crate depending on `ecto_changeset`.
The library builds an Ecto changeset from the definition, and the crate
does the same with the crate that already has Ecto's cast, validations,
messages and options, so errors match down to the options.

* **Inside `ecto_changeset`**: rejected, that crate is "Ecto in Rust" and
  shouldn't know SurveyJS.
* **Inside the Tauri app**: rejected, a mobile app or any other Rust
  client would need it too, and it mirrors a library, not the app. It also
  could move to the `dynamic_form` repository one day.

### Parity with the library, its quirks included

The crate does what the library does, for every definition the library
reads in data mode except file uploads. Where the library behaves oddly,
the crate copies it, so the two apps never disagree; the oddities are
listed under "What the Rust copies from the library", to fix in the
library and then here.

So the crate reads a definition as `Parser.FromData` does: unknown keys
and validator types are ignored, an element without a known type falls
back the same way, and a question type the library doesn't know is a
string field that renders nothing. It refuses, with the reason, only what
the library would crash on when rendering or validating (an element
without a name, a non-string condition, a `rateStep` below 1, which
never stops rendering, an unknown `groupType` or `choicesFromQuestionMode`),
a `file` question, which needs its own work, and a regex the `regex`
crate can't compile.

Alternative: refuse every feature not yet ported, which the first version
did with `deny_unknown_fields`. That was right while the crate covered a
subset; with the whole of data mode covered, refusing what the library
accepts would itself be a difference.

### Parity through a shared case file

`native/dynamic_form/tests/cases.json` is what the library does, in four
parts, and `mix test` holds the library to it while `cargo test` holds
the crate:

* `cases`: definitions, params and the errors they give, a nested
  entry's under `name.index.field`, and the changes when a case lists
  them, for rules that change a value without an error.
* `expressions`: conditions and what they evaluate to over raw params.
* `views`: what a form shows for params, before and after a failed
  submit, as an outline: one line per control (name, value, checked,
  disabled, readonly), error, heading, note and button. The Elixir test
  reads it from the HTML the library renders through
  `App.Web.CoreComponents`; the Rust test builds it from the view, as
  the Svelte components render it.
* `flows`: the lifecycle, run through `DynamicForm.form` in
  `App.DynamicFormFlowLive` with LiveViewTest events, and through
  `DynamicForm` in Rust: mount from data, changes, entries added and
  removed, submits, with the outline after each step and each submit's
  data. A change sends the form's current values with the step's over
  them, as LiveViewTest and a browser do.

A new case is written as input only. `mix test --only record_cases`
fills in what the library does, which is then read before it's trusted,
and the crate made to match. When a library upgrade changes anything,
the Elixir test fails first.

Alternative: run the Rust in the Phoenix app through a NIF, as universal
changesets do, and compare live. Rejected for now: the web app uses the
library as is, with no Rust in its form path, so a static contract is
enough and keeps the NIF crate (generated by `mix app.rust`) out of it.

Errors compare as `[field, message, [[option, value], ...]]`. One
normalization: Ecto keeps a number question's bound as a `Decimal`, the
crate as a JSON number, so the Elixir test writes a `Decimal` as a
number. The shown message is identical.

### Rust builds the view, Svelte only renders it

`view` returns, per question, the component name, its props and the
description. `DynamicForm.svelte` looks the component up and spreads the
props. This follows `tauri/AGENTS.md` (logic in Rust, thin JS), and keeps
the props step in one place per platform, `input/1` and `view`, both
tested.

Alternative: send the definition to Svelte and build props in JS. Less
IPC, but a third copy of the props logic, and untested by `cargo test`.

### Validation on every change, latest reply wins

Like LiveView, the desktop form validates on every `input` event: a local
`invoke` round trip is far under a frame. Each request carries a counter
and only the latest reply is applied, so a slow reply never overwrites
what the user typed since.

Errors follow the library: none while the user first types, since the
component's changeset has no action until a submit fails, then every
error of a field that is in the params. The first version showed errors
on any input the user had used, LiveView's used-input rule, which the
library's component never reaches before a submit.

### The page holds the form's state

The library's component keeps its changeset between events, and merges
each change over it: the initial data, then what the form holds, then
what the browser sent. That is what keeps a hidden section's values, and
the entries' ids, when the browser stops sending them. The crate is
called once per event and keeps nothing, so each view comes with a
`FormState`, the params its changeset was built from and whether a submit
has failed, and the page sends it back with the next event.

Alternative: keep the state in the Tauri process, keyed by form. Fewer
bytes over IPC, but state to clean up, and a form remounted by the page
would have to say so.

### `DynamicForm.svelte` takes callbacks, not `app:emit`

It takes `onchange(entries, state)`, `onsubmit(entries, state)`,
`onadd(path, state)` and `onremove(path, index, state)` props. The
generated components use the `app:emit` context for `phx-*` events,
because they mirror HEEx that names events. `DynamicForm.svelte` is
hand-written and owned by the page using it, so plain callback props are
clearer, and a page with two forms needs no event-name routing.

### A definition is a function beside its LiveView, marked `@universal_dynamic_form`

A form is defined where it's used, as Phoenix puts a form's code with its
LiveView, never in a central forms module. The definition is a plain
function returning the JSON as an Elixir map, which the web app calls; a
LiveView whose form only the web shows needs nothing more. Marking it
`@universal_dynamic_form true` is the opt-in for the other apps, as
`@universal_component` and `@universal_changeset` are: `mix
app.dynamic_forms` writes `<function>.dynamic_form.json` beside the
module, which the desktop app includes by path, and `mix test` fails
while the file is out of date. A marked function takes no arguments,
since it's called once to write the file, and returns JSON data only, so
the web and the file hold the same definition.

Choices that depend on the user, like their communities, are `[]` in the
definition and filled in by `PostsLive.post_form/1` and
`forms::post_form/1`.

Alternatives considered:

* **Hand-written JSON files**, which this was at first, in
  `lib/app/web/forms` with an `App.Web.Forms` module to load them. Both
  apps read one file with no generator, but it isn't how a Phoenix app
  defines things, and it puts every form in one place.
* **A function that takes the runtime values**, like the communities.
  The file can't hold them, so the function's value would differ from
  the file.

`PostsLive` parses the definition once, in `mount`. Passing the raw map to
`DynamicForm.form` would re-parse it on every render, and the parser gives
a definition without an `"id"` a random one, which makes the component
think the definition changed and reset what the user typed. The
definition has an `"id"` for the same reason.

### The form rules and the changeset both check, separately

The form requires a body of at most 10,000 characters, and so does
`Post.changeset/3`. The form's rules are what the user sees as they type.
The changeset is the authority, run by `Posting.write/3` on the server
and `store::write_post` on the device. The two are kept apart on
purpose, not derived one from the other: a form often collects data that
goes through several flows and changesets before it's saved, so a form's
rules are about the form, and a changeset's about its table.

### Error text is English in Rust

The web app translates errors with Gettext through
`CoreComponents.translate_error/1`. The Rust interpolates Ecto's message
template (`Error::text`), which equals the untranslated English. A
translated desktop app needs the `errors.po` catalog in Rust.

## What the Rust supports

Everything the library reads in data mode, except file uploads:

| Part | Supported |
| --- | --- |
| Questions | `text` (any `inputType`; `number` casts as a decimal, `email` checks the format), `comment`, `dropdown`, `radiogroup`, `checkbox`, `boolean`, `rating`, `tagbox`, `paneldynamic`, and types the library doesn't know |
| Elements | `panel` (`groupType` `horizontal` or `vertical`), `html`, `image`, and `pages`, flattened with their titles as headings |
| Conditions | `visibleIf`, `enableIf`, `requiredIf`: comparisons, `empty`/`notempty`, `contains`, `anyof`/`allof`/`noneof`, `and`/`or`, parentheses, `{panel.field}` |
| Question settings | `title`, `placeholder`, `description`, `defaultValue`, `choices` (strings, numbers, booleans, `{value, text}`, `[text, value]`), `isRequired`, `requiredLabel`/`requiredMark`, `readOnly`, `rateMin`/`rateMax`/`rateStep`, `metadata.style` |
| Carry forward | `choicesFromQuestion` from a nested form or a choice question, `choiceValuesFromQuestion`, `choiceTextsFromQuestion` with `{field}` and `{panelIndex}`, `choicesFromQuestionMode`, `noChoicesText` |
| Nested forms | `templateElements`/`questions`, `templateTitle`, `panelCount`, `minPanelCount`, `maxPanelCount`, `allowAddPanel`, `allowRemovePanel`, `addPanelText`, `removePanelText`, `noEntriesText`, `confirmDelete`, `confirmDeleteText`, `keyName`, `keyDuplicationError`, `defaultPanelValue`, `generateIds` |
| Validators | `text` (min/max length), `email`, `numeric` (min/max value), `regex`, each with `text` as the message; other types do nothing |
| Lifecycle | initial data, defaults, seeded entries and their ids, changes keeping what the browser doesn't send, entries added and removed, submits |

Not supported:

* `file` questions: refused, since the library's uploads are their own
  piece of work, not fully built there either.
* What the component takes as attributes rather than JSON:
  `custom_field_types`, `validation_summary`, `on_change`/`on_submit`
  callbacks, `change_debounce_in_ms`. The app uses none of them.
* The component disabling every field while a submit is in flight; the
  desktop disables the submit button only. The component sets and clears
  it within one event, so the web never renders it either.

Known differences, none in the app's forms:

* Regex validators run on the `regex` crate, not PCRE: a pattern with
  lookaround or backreferences fails to load, and `$` doesn't match
  before a final newline. The built-in email format is rewritten to
  match PCRE exactly.
* Numbers are `f64` in Rust and `Decimal` in Ecto: they compare the
  same for the bounds a form uses, and a number field shows what was
  typed, but a carried-forward label built from a number entry's field
  writes `5.0` where the library writes `5`.

## What the Rust copies from the library

Behaviors that look like bugs, copied so both apps agree, and each
recorded in `cases.json`. Fix them in the library, then here:

1. **Rendering reads the cast values, validation the raw params.** A
   number question's value is a `Decimal` when rendering, which compares
   to nothing, so `visibleIf: "{age} > 60"` never shows its question
   while `requiredIf: "{age} >= 18"` works.
2. **Over raw params, `false` reads as `nil`.** A `false` from initial
   data makes `{agree} notempty` false. A checkbox group's hidden `""`
   makes it `notempty` before anything is ticked.
3. **A question in a hidden panel is still required**, since only its
   own `visibleIf` counts, and a required nested form ignores conditions.
4. **A field absent from the params shows no errors**, even after a
   failed submit: a required radio group with nothing picked fails the
   submit without saying why. `used_input?/1` needs the key.
5. **Inside a nested entry, `enableIf` reads only the entry's values**,
   where `visibleIf` reads the form's too.
6. **Entries are validated differently when rendering.** The renderer
   builds them without the form-level questions, so a carried-forward
   source at the top level doesn't prune an entry's values on screen,
   only on submit.
7. **After a valid submit the form keeps showing its last state**, errors
   included, until the parent remounts it.
8. **A required checkbox group whose values are all dropped passes**, see
   item 8 of the feedback below.

## How it was verified

* `mix test`: the library against `cases.json` (errors, conditions,
  outlines, flows); `CoreComponents` markup for every question type;
  `PostsLive` writes a post, lists communities as choices, rejects a
  blank and a too-long body, and resets after posting.
* `cargo test` in `native/dynamic_form`: the crate against `cases.json`,
  and unit tests of parsing, Elixir's number parsing and float writing,
  conditions, nested entries and the view. The parity tests were checked
  by breaking the crate on purpose: dropping the `Decimal` rule, the
  errors' order, the held params or the defaults each fails them.
* `cargo test` in `tauri/src-tauri`: the post form's choices, errors
  waiting for a failed submit, a valid submit's post and an invalid
  submit's form.
* `svelte-check` and the Vite build: the generated Svelte,
  `DynamicForm.svelte` and `DynamicFormElements.svelte` type-check, and
  the desktop CSS has the library's classes.
* **Same markup, checked once by hand** in the first version: the Rust
  view rendered by `DynamicForm.svelte` through Svelte's server renderer
  and the library's HTML had identical DOM trees. The outlines now check
  the content of every view automatically; the markup of
  `DynamicFormElements.svelte`, copied from the library's templates, has
  not been compared that way.

Not checked by clicking: the desktop app itself, since this Mac's shell
can't drive its window.

## Feedback for the `dynamic_form` library

Things that came up here, roughly by value. Each is a proposal to
discuss, not a change made.

1. **Expose the rules as data.** `create_changeset/3` interprets the
   definition into Ecto calls internally. A public
   `DynamicForm.Changeset.rules(instance)` returning the types map and an
   ordered list of `{field, validation, options}` would let any runtime
   run the same rules with an Ecto port, without reimplementing the
   SurveyJS interpretation, which is most of what `native/dynamic_form`
   does. The Rust would shrink to "cast with these types, apply these
   validations", the same shape as universal changesets.
2. **Expose the view as data.** Likewise, the step from question to
   component and assigns lives in private `render_question/3` clauses. A
   public function returning `[%{component: :input, assigns: ...}]` per
   question would let other renderers reuse it, and let a test compare
   the web's assigns with the Rust's directly.
3. **Make the question wrapper a component.** Each question is wrapped in
   `<div class="mb-4">` and followed by
   `<p class="mt-2 text-sm text-gray-500">` for the description, in the
   renderer itself. As a components-module function (`question/1`), the
   whole form would be component-driven and `DynamicForm.svelte` could
   be generated too. The submit wrapper is the same case.
4. **Pass `type` and `disabled` inside `rest` to `button/1`.** A
   Phoenix 1.8 generated `button/1` renders only `rest`, so with the
   library's call it drops `type` and, more importantly, `disabled` while
   submitting: Phoenix gathers undeclared assigns into `rest` only when no
   `rest` is given. This app's `button/1` declares both. The styling
   guide's example button reads `@type` and `@disabled`, so putting them
   only in `rest` would break buttons written from it; passing them in
   both would render them twice on such a button.
5. **A stable id for parsed definitions.** `Parser.FromData.parse!/1`
   gives a definition without `"id"` a random one. Passed as a map, the
   definition parses differently on every render, and the LiveComponent's
   update guard then resets the user's input. A deterministic id (a hash
   of the definition), or leaving the id out of the guard's comparison,
   would avoid that trap.
6. **A reset after success.** Clearing the form after a valid submit
   needs a new component id today. A `reset_on_success` attribute, or a
   reset through `send_update/3`, would say what it means.
7. **Fixed in 1.1.1: `"requiredLabel": false` didn't suppress the mark
   in data mode.** The parser read `requiredLabel || requiredMark`, so
   `false` fell through to the default `*`. The Rust no longer copies it.
8. **Fixed in 1.2.0: choices weren't validated.** A choice question now
   drops values not among its choices, and a rating rejects values
   between its steps; the Rust does both, and `cases.json` checks the
   resulting changes. One gap remains: a required `checkbox` or `tagbox`
   whose values are all dropped is left as `[]`, which
   `validate_required` counts as present, so it passes where the
   changelog says it errors with "can't be blank". A single-value
   question is deleted from the changes and does error. Turning an
   emptied list into `nil`, as `normalize_array_params` does for an
   all-blank submission, would close it. The Rust copies the gap, and the
   case "choices not offered are dropped, which leaves a required group
   empty but present" records it.
9. **Fixed in 1.1.1: the email format allowed a final newline.**
   `^[^\s]+@...$` in PCRE matched `"a@b.c\n"`; it is anchored with `\A`
   and `\z` now, in the library and the Rust, and `cases.json` has the
   case. A definition's own regex validators still use its `$` as
   written.
10. **Pass a boolean's description separately.** It's merged into the
   label as safe HTML, which a non-HTML renderer can't take apart.
11. **`isRequired` on a boolean accepts `false`.** That is Ecto's
   `validate_required` semantics, but a required checkbox usually means
   "must be ticked". Documenting it, or mapping it to
   `validate_acceptance`, would help.
12. **The behaviors under "What the Rust copies from the library"**,
   found while porting: conditions reading cast values when rendering
   and raw params when validating, `false` as `nil`, required questions
   in hidden panels, no errors for fields absent from the params, entry
   `enableIf` scope, entries validated without the form-level questions
   when rendering, and the form keeping its state after success.
